写 Java 服务时，我越来越少追求“看起来很高级”的抽象，而是优先确认边界是否清楚。

一个服务最先应该回答三个问题：它负责什么，不负责什么，失败时应该如何被观察到。

## 边界比技巧重要

Controller 不应该塞业务判断，Service 不应该知道太多 HTTP 细节，Repository 也不应该悄悄吞掉数据异常。层次的意义不是制造文件夹，而是让问题发生时能快速定位。

## 配置要可解释

配置项越多，系统越像一台没人敢碰的机器。我更喜欢少量明确的配置，并给关键配置留下默认值、范围和注释。

## 日志不是越多越好

有价值的日志应该能回答“谁在什么时候，对什么资源，做了什么，结果如何”。否则它只是噪音。
